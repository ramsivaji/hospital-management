Clinic Booking System: Architecture and Build Blueprint
An agent-agnostic plan: if one AI tool (Antigravity) runs out of tokens, another (VS Code + any agent) picks up exactly where it stopped.
1. The golden rule: the repo is the memory
Chat history disappears when tokens run out or you switch tools. So nothing important may live only in a chat. Every decision, task, and status lives in files inside the repository. Any agent, in any tool, starts a session by reading the same few files and can continue immediately.
Three principles make this work:
• One source of truth: AGENTS.md (rules) + docs/PROGRESS.md (status) + docs/tasks/ (work items).
• Contract first: backend and frontend never talk to each other directly. They both obey openapi.yaml, so two agents can build in parallel without a conversation.
• Small, committed steps: one task = one branch = small commits. Commit before you stop, always. An uncommitted change is a lost change.

# Agent Rules (read this first, every session)

## Start of session
1. Read docs/PROGRESS.md, then the task file named under Next Action.
2. Run `git status` and `git log -5`. Finish or stash any unfinished work.
3. Run `make test` to confirm the starting state is green.

## While working
- Work on ONE task at a time, on branch task/T-xxx-short-name.
- Never change openapi.yaml by hand: change the Django serializers/views,
  then run `make contract`.
- Never hand-edit frontend/src/api/generated.
- Business logic lives in services.py; reads in selectors.py; views stay thin.
- Every service function gets tests. Booking and availability need 80%+ coverage.
- Animate only transform and opacity. Respect prefers-reduced-motion.
- No secrets in code. Use env vars listed in .env.example.
- Do not install new dependencies without adding a line to docs/DECISIONS.md.

## End of session (or when tokens are low)
1. Commit with message: T-xxx: what changed.
2. Update the task file checkboxes and notes.
3. Update docs/PROGRESS.md: status table + Next Action (one precise sentence).
4. Push the branch.

5. Working in parallel: contract first
Because backend and frontend only meet at openapi.yaml, two agents (or you and one agent) can work at the same time and never need to exchange messages.
• Backend agent builds Django to satisfy the contract, then regenerates it with make contract (drf-spectacular).
• Frontend agent generates TypeScript types and an API client from the contract (for example with openapi-typescript) and develops against mock responses (MSW) until the real API is ready.
• Contract changes go through a small pull request that touches only openapi.yaml and a one-line note in DECISIONS.md. Both sides then rebase.
• CI check: the pipeline regenerates the contract and fails if it differs from the committed file, so drift is impossible.
Track A (backend)   ──► serializers/views ──► make contract ──► openapi.yaml ◄── pulls ── Track B (frontend)
                                                                    │
                                                          generate types + MSW mocks
Tool switching in practice: the tool does not matter, the branch does. Antigravity stops, you open the same repo in VS Code, run the session-start prompt from section 9, and the new agent reads PROGRESS.md and continues.

You are continuing an existing project. Do not start from scratch.

2. Run git status and git log -5, then make test. Report the state in 5 lines.
3. Work only on the Next Action task. Follow acceptance criteria exactly.
4. Commit small and often on the task branch.
5. Before you run low on context, do the End of session steps in AGENTS.md.
Ask me only if a requirement is ambiguous.

Stop adding features. Run the End of session steps now: commit, update the task
file checkboxes, rewrite Next Action in docs/PROGRESS.md as one precise sentence
including any failing test names, and push.
